# AI駆動開発のトークン消費：まず測る、そして仕組みで減らす

## はじめに

前回は、AIに任せる範囲を広げるときに引くべき一線——**secretsをAIに見せない設計**——を扱いました。「見せない」という発想でコンテキストを絞る話でしたが、今回はそこから地続きの、もう少し日常的なテーマです。

AIコーディングを続けていると、必ず気になってくるのが**トークン消費**です。使用量の上限に早く到達する、APIの料金が思ったより高い、コンテキストがすぐ一杯になる。こうした悩みに対して、世の中には削減テクニックの情報があふれています。

ただ、最適化には鉄則があります。**測ってから減らす**、です。何がトークンを食っているかは、人によってまったく違います。ファイル読み込みが大半を占める人もいれば、テストやビルドの出力が太い人もいます。自分の環境を知らないまま対策を打つと、効いているかどうかすら分かりません。

本記事では、自分の消費を**実測する方法**と、多くの環境で見落とされがちな**2つの消費源**、そして**フックで削減を自動化する**考え方を紹介します。

> なお、以下の例はClaude Code固有の仕様を含みますが、「実データから測る」「指示ではなく仕組みで強制する」という考え方自体は、他のAIコーディングエージェントにもそのまま応用できます。

## まず組み込みコマンドで、そしてその限界を知る

Claude Codeには消費を確認するコマンドが2つあります。

**/context** は、現在のコンテキストウィンドウの内訳を表示します。システムプロンプト、ツール定義、メッセージがそれぞれ何％を占めているかが分かります。

**/cost** は、そのセッションで消費したトークン量とコストを表示します。

日常的にはこの2つで十分です。ただし、どちらも**今この瞬間・このセッションのスナップショット**でしかありません。「先週と比べて増えているのか」「どのツールが主因なのか」「導入した削減策は累計でどれだけ効いたのか」——こうした問いには答えられません。

傾向と内訳を知るには、実データにあたる必要があります。

## セッション記録から実測する

Claude Codeは、セッションの全記録（transcript）をJSONL形式で保存しています。場所は **~/.claude/projects/プロジェクト名/セッションID.jsonl** です。

この中のassistantメッセージには、**message.usage** としてトークンの実数が記録されています。見るべきフィールドは4つです。

**input_tokens** はキャッシュされていない入力、**cache_creation_input_tokens** はキャッシュへの書き込み、**cache_read_input_tokens** はキャッシュからの読み込み、**output_tokens** は出力です。

さらに、どのツールを呼んだかを示す **tool_use** ブロックと、その結果本体である **tool_result** ブロックを **tool_use_id** で突き合わせれば、「どのツールが何トークン分の結果をコンテキストに積んだか」というツール別の内訳まで集計できます。

自分でスクリプトを書かなくても、「どのフィールドを見ればいいか」さえ知っていれば、jqや簡単な集計スクリプトで測れます。AIに「このJSONLからツール別のトークン消費を集計して」と頼むのも手です。

> ひとつ注意があります。このJSONLはClaude Codeの**内部形式**で、公式ドキュメントにも「バージョン間で変わりうるため、直接パースするスクリプトはリリースのたびに壊れる可能性がある」と明記されています。恒久的な仕組みにするのではなく、「一度測って現状を知る」用途に割り切って使うのが安全です。

もうひとつ、トークン数ではなく**文字数**で代用して集計する場合は、**画像とバイナリを必ず除外**してください。transcriptには画像がbase64文字列として埋め込まれており、1枚で数十万文字に膨らみます。除外しないと、画像が最大の消費源であるかのように見えてしまいます。実際の画像は画素数ベースで課金されるため、トークンに換算すると意外と小さいことが多いです。

## 見落としがちな消費源①：同じファイルを何度も読む

実際にtranscriptを眺めると、**同一セッション内で同じファイルを何度も読み直している**ことが珍しくありません。原因は大きく3つに分けられます。

ひとつめは**編集後の再読**です。編集した結果を確認するために読み直すパターンですが、編集が成功したかどうかはツールの実行結果で分かるため、多くは不要です。

ふたつめは**純粋な重複**です。編集も要約も挟んでいない、特に理由のない読み直しで、これは完全に回避できます。

みっつめは**コンパクション後の再読**です。会話の要約で内容が失われたための再取得なので、これは正当な読み直しです。ただし、多くの場合は必要な範囲だけの部分読みで足ります。

見落とされやすいのは、「1回の読み込みが大きすぎる」ことだけでなく、「**同じものを何度も読む**」ことが独立した消費源になる点です。エージェントは毎ターン会話全体を読み直すため、重複して積まれた内容は、セッションが続く限り繰り返しコンテキストに載り続けます。

## フックで削減を「強制」する

では、どう避けるか。「同じファイルを読み直さないで」とCLAUDE.mdに書く方法もありますが、CLAUDE.mdの指示は **advisory（助言）** です。AIが従わない可能性が常に残ります。

確実に止めたいなら、**フック（hooks）** で実行そのものをブロックします。Claude Codeの **PreToolUse** フックは、ツール実行の直前に任意のスクリプトを走らせる仕組みです。スクリプトは標準入力からセッションIDやツール名などを含むJSONを受け取り、**終了コード2で終了するとツール実行がブロックされ、標準エラー出力の内容がエラーメッセージとしてAIに返ります**。

つまり「拒否したうえで、代わりにどうすべきかをAIに伝える」ことができます。

重複読み対策のフックは、**誤検知のリスクが最も低い条件だけ**で判定するのがコツです。そのファイルの初回の読み込みは許可、前回読んだときからファイルの更新時刻（mtime）が変わっていれば許可、範囲指定つきの部分読みも許可（部分読みは安価なので）。それ以外の再読だけを拒否します。

実装は「標準入力のJSONから対象ファイルパスを取り出す → セッションごとの読み込み記録と照合する → 重複なら標準エラーにメッセージを出して終了コード2、それ以外は0」という3ステップのシェルスクリプトになります。骨格はこうです。

```bash
#!/bin/bash
# 同一セッション内の重複 Read をブロックする PreToolUse フック
# 異常時はすべて「許可」に倒す（fail open）
command -v jq >/dev/null 2>&1 || exit 0

IFS=$'\t' read -r session file offset limit <<<"$(jq -r \
  '[.session_id // "", .tool_input.file_path // "",
    (.tool_input.offset // "" | tostring),
    (.tool_input.limit // "" | tostring)] | @tsv')"

if [ -z "$session" ] || [ -z "$file" ]; then exit 0; fi  # 情報不足 → 許可
if [ -n "$offset" ] || [ -n "$limit" ]; then exit 0; fi  # 部分読み → 許可
[ -f "$file" ] || exit 0

state_dir="${TMPDIR:-/tmp}/dedupe-read/$session"
mkdir -p "$state_dir" 2>/dev/null || exit 0
key=$(printf '%s' "$file" | shasum | cut -d' ' -f1)
mtime=$(stat -f %m "$file" 2>/dev/null || stat -c %Y "$file" 2>/dev/null)
[ -n "$mtime" ] || exit 0

prev=$(cat "$state_dir/$key" 2>/dev/null)
echo "$mtime" > "$state_dir/$key"

if [ -n "$prev" ] && [ "$prev" = "$mtime" ]; then
  echo "このファイルは読み込み済みで内容も変わっていません。必要なら範囲を指定して読んでください。" >&2
  exit 2
fi
exit 0
```

あとは **~/.claude/settings.json** に、Readツールの直前にこのスクリプトを実行する設定を追加するだけです。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Read",
        "hooks": [
          { "type": "command", "command": "~/.claude/hooks/dedupe-read.sh" }
        ]
      }
    ]
  }
}
```

ポイントは、拒否のメッセージが単に「ダメ」ではなく**逃げ道を示している**ことです。「必要なら範囲を指定して読んでください」と案内することで、コンパクション後の正当な再読を完全には塞がず、全体読みではなく安価な部分読みへ誘導できます。

## fail open と fail closed：異常時にどちらへ倒すか

フックを自作すると、必ずぶつかる設計判断があります。**フック自体が壊れたとき、許可に倒すか（fail open）、拒否に倒すか（fail closed）**。

答えは一律ではなく、**損害の非対称性**で決めます。

lintやテスト、secrets検査のような**品質ゲートは fail closed（拒否）** です。素通りすると「守られているつもりで無防備」という最悪の状態になり、しかも成功と区別がつきません。

一方、今回の重複読みブロックのような**読み込み抑制は fail open（許可）** です。壊れたときに全ファイルの読み込みが止まってしまうと、作業そのものが完全に停止してしまいます。

先ほどのスクリプトの随所に「異常なら exit 0」が置かれていたのは、まさにこの判断の現れです。「安全側に倒す」という言葉の意味が、ケースによって正反対になる——ここがフック設計の一番の学びどころだと思います。

## 見落としがちな消費源②：設定ファイルの肥大化

もうひとつ、多くの環境で見直す価値があるのが、**毎セッション自動で読み込まれる設定類**です。CLAUDE.mdと、そこから **@import** されているファイル群がこれにあたります。

これはセッションのたびに必ず支払う**固定費**です。フレームワークや設定集を導入するたびに @import が積み上がり、放置すると数千から数万トークン規模に膨らむこともあります。CLAUDE.md本体を短く保つのは基本ですが、**@import 先まで含めた合計の投入量**で棚卸しすることが重要です。

溜まりやすい「死荷重」は典型的に3種類あります。

**使わなくなったフレームワークやモードの説明**は、@import の行を外します。参照先のファイル自体は削除しません。

**無効化・削除済みのMCPサーバーの解説ドキュメント**も要注意です。MCPサーバー本体を外す操作をしても、CLAUDE.mdから @import している解説ドキュメント側は消えません。サーバーを外すときは、対応する @import も同時に外しましょう。

**特定のプロジェクトでしか使わないルール**がグローバルのCLAUDE.mdに書かれている場合は、削除ではなく**そのプロジェクトのCLAUDE.mdへ移動**します。プロジェクト配下のCLAUDE.mdはそのプロジェクトでのみ読み込まれるため、他の作業の固定費になりません。

共通の原則は「**いきなり削除しない**」です。外し方を誤ると、必要になったときに戻せなくなります。

## HTMLコメント：トークンゼロでメモを残す

棚卸しで一番困るのは「消してしまうと後で戻せない」ことです。ここでClaude Codeの公式仕様が役立ちます。

**CLAUDE.md内のブロックレベルHTMLコメントは、コンテキストに投入される前に除去されます**。つまり、**トークンを1つも消費しません**。

これを使えば、無効化した設定の復元手順をCLAUDE.mdに書き残しておいても、**人間には見えて、AIのコンテキストには一切載らない**メモになります。

```markdown
# Global Instructions

@my-rules.md

<!--
Framework X — 2026-06-01 に常時ロードを停止
理由: 常時ロードの @import 群が数万トークン規模に達していた
戻すには: 下の1行を @import に戻す
FrameworkX/MODES.md ほか
-->
```

ちなみに、バッククォートで囲んでコードブロック化しても @import は無効化できますが、その場合は**テキスト自体はコンテキストに載る**ため、トークンを消費します。メモを残すならHTMLコメント一択です。

あわせて、無効化するときは**ファイルを削除せず @import の行を外すだけ**にしておくと、フレームワークの再インストールと衝突せず、1行の変更で元に戻せます。

## まとめ

要点を4つにまとめます。

**測ってから減らす。** /context と /cost は現時点のスナップショットです。傾向とツール別の内訳は、セッション記録から実測できます。ただし内部形式なので「現状把握」用途に割り切って使いましょう。

**見落としがちな消費源は2つ。** 「同一ファイルの重複読み」と「肥大化した設定ファイル」です。どちらも多くの環境で起きうるので、一度自分の環境を確認する価値があります。

**確実に止めたいなら、指示ではなく仕組みで。** CLAUDE.mdの指示は助言にすぎません。PreToolUseフックで強制しましょう。異常時に倒す方向は、損害の非対称性で決めます。品質ゲートは fail closed、読み込み抑制は fail open です。

**設定の棚卸しは「外す・移す」で。** いきなり削除せず、復元手順はHTMLコメントでトークンゼロで書き残せます。

ここまでが「測る・無駄を止める」段階です。まずは自分のセッション記録を一度覗いてみてください。想像とまったく違う内訳が見えてくるはずです。

より詳しい仕様は、[Manage Claude's memory — Claude Docs](https://code.claude.com/docs/en/memory)（@import とHTMLコメント）と [Hooks reference — Claude Docs](https://code.claude.com/docs/en/hooks)（PreToolUseの入出力と終了コード）を参照してください。
